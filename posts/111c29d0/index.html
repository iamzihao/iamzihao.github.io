    Tokenizer 转换表入门：prompt 怎么变成 token id，又怎么回到文字

    Posted on 2026-09-17 Views: Word count in article: 14k Reading time ≈ 26 mins.

    链路上抓到一串整数时，它很可能就是 token id——大模型不认字，只认编号。要把这串编号变回人能读的文本，需要一张 id 到字节的对照表，本文称之为转换表；而这张表在不同模型之间并不通用。

    本文沿着一次完整推理把数据形态走一遍：文本怎么被切成 token、token 怎么变成 id、id 送上 GPU 之后发生什么、生成的 id 又怎么回到文本。最后落到抓包场景——手上只有一串来路不明的整数，怎么用几张表把它试解成文本。文中数字全部来自本机真实跑出来的结果，词表取自 Qwen2.5-0.5B-Instruct 和 GPT-2 的公开 tokenizer.json。

    📚 基本概念速读

    名称 定义 记忆点
    token 模型处理文本的最小单位 比字粗、比词细的碎片
    tokenizer 负责文本与 token 互转的程序 编码器与解码器合体
    词表（vocab） token 与 id 的对照表 一本字典，行号即 id
    BPE Byte Pair Encoding，按频率合并相邻字节对的切分算法 主流词表的生成方式
    token id token 在词表里的整数编号 模型真正看见的东西
    embedding 把 id 查成向量的那张表 数字进入网络的入口
    logits 最后一层输出的分数，长度等于词表大小 每个候选 token 的得分
    prefill / decode 处理 prompt 与逐 token 生成两个阶段 一次大计算 + 多次小计算
    转换表 id 到字节（或文本）的映射 反查文本的依据

    能看出来整条链上的数量级变化：76 B 的编号 → 33 KiB 的向量 → 594 KiB 的分数 → 又是 4 B 的编号。抓包看到的往往是两头的小数据，中间的大块计算留在显存里。

    往下按这条链路的顺序拆。前两段（文字到 id）完全在 CPU 上完成，跟模型权重无关，可以离线跑；第三段在 GPU 里；第四段又回到 CPU。

    ✂️ 文本怎么变成 token

    为什么要切

    模型的输入是一串整数，每个整数必须是词表里的合法编号，所以文本要先切成一堆片段再逐个编号。按字符切，字符集本身就有几万个，标点和大小写还得分开放；按空格切词，词表会跟着语言和领域无限膨胀，遇到没见过的词（OOV，out-of-vocabulary）就没法编码。

    折中方案是子词（subword）：高频片段保留成整块，低频内容退化成更小的碎片。常见做法是 BPE。

    BPE 的直觉

    BPE 原是一种数据压缩算法，思路很朴素：先从最小的单位开始，统计哪对相邻单位出现最多，就把它们合并成一个新单位，重复到词表规模达标为止。

    真实词表里的 merges 列表记录了每一次合并。Qwen2.5 的 tokenizer.json 里 merges 有 151387 条，开头几条是：

    Ġ 不是乱码，它是空格（0x20）在词表里的写法，下一节解释。

    BPE 生成的词表有一条清晰的账：

    模型 初始字节 merges 次数 词表条目 特殊 token 最大 id
    Qwen2.5 256 151387 151643 22（单独登记） 151664
    GPT-2 256 50000 50257 1（本来就在词表里） 50256

    Qwen2.5 的 256 加 151387 正好等于词表条目 151643，再叠加 22 个特殊 token；GPT-2 的 50257 条里已经包含了 <|endoftext|>，所以 merges 加初始字节只有 50256。

    这些特殊 token 在抓包时是会真的出现的：Qwen2.5-0.5B-Instruct 的 config.json 里 eos_token_id = 151645，正是 <|im_end|>。多轮对话的 prompt 用 <|im_start|> 和 <|im_end|> 包住每一轮，采样到 <|im_end|> 就意味着本轮结束。所以转换表要把它们和 BPE 条目一起收进来（Qwen2.5 的 id 口径是 151665 条，最大 id 151664），漏掉就解不出轮次边界。

    初始单位是 256 个字节，不是字符。这是 byte-level BPE 的关键：任何文本（汉字、emoji、二进制残留）先转成 UTF-8 字节，都能被这 256 个基本单位表示，于是永远不会有 OOV，也永远能还原。

    从文字到字节，再到 token

    这几个层次容易混在一起，拿 你好 两个字过一遍就清楚了：

    同一段文字，不同模型切出来的结果差得很多（实测）：

    模型 token 数 切出来的片段 对应 id
    Qwen2.5 1 ä½łå¥½（整块 你好） 108386
    GPT-2 4 ä½ ł å¥ ½ 19526 / 254 / 25001 / 121

    Qwen2.5 词表里把 你好 当成一个整体，一个 token 装下两个字；GPT-2 词表里几乎没有中文，只能退回字节，6 个字节被切成 4 段——你 的三个字节 e4 bd a0 被拆成了 e4 bd 和 a0 两段。

    三点值得记住：

    • 字节层是永远有路可退的那一层。词表里没有的字符，BPE 就退回单字节表示，所以任何文本都能编码，也都能还原——后面关于可逆性的讨论都建立在这上面。
    • token 数不等于字符数。同样两个汉字，Qwen2.5 用 1 个 token，GPT-2 要 4 个。
    • 模型看到的只有 id。文字、字节、token 片段都是中间形态，真正进网络的是 108386 这个整数。

    抓包时能看到的也是最后那一层：一串 id。要把它变回文字，靠的就是从 id 反查回字节的那张表。

    Ġ 到底是什么

    既然基本单位是字节，词表里就该有空格、换行这些不可打印字节。为了让词表能用纯文本保存（一个 tokenizer.json 或一份 merges 文件），GPT-2 定义了 bytes_to_unicode 映射：把 256 个字节一一对应到 256 个可见字符，空格（0x20）映射成 Ġ（U+0120），换行（0x0A）映射成 Ċ（U+010A），其余可打印字节保持原样。

    🔢 token 怎么变成 id

    id 只是行号

    词表是一份有序对照表，id 就是行号。它没有语义，也没有跨模型含义：Qwen2.5 的 53702 是 PCI，GPT-2 的 53702 是另一个完全无关的片段。同一句中文，两个模型的 token 数也差很多：

    文本 字符数 汉字数 Qwen2.5 token 数 GPT-2 token 数
    PCIe 链路上抓到的 token id，能还原出原来的问题吗？ 32 16 19 44
    大语言模型的推理过程分为预填充和解码两个阶段。 23 22 15 54
    Hello, how are you today? 25 0 7 7

    中文语料喂得多的 Qwen2.5 把常用汉字组合并进了词表（一个 token 常常覆盖两个汉字），GPT-2 词表里几乎没有中文，只能退回到字节，于是同一个汉字要 3 个 token 表示。同样一句中文，GPT-2 的 token 序列比 Qwen2.5 长出一倍以上，反查时要拼的片段也更多。

    config.json 里的 vocab_size 和词表长度也不总相等：Qwen2.5-0.5B 的 config 写 151936，tokenizer.json 里实际 151665 条，多出来的行是预留 id。反查时用 id 当数组下标，预留区永远查不到东西，越界判断要用词表长度，而不是 config 的值。

    特殊 token 不在 BPE 表里

    Qwen2.5 有 22 个特殊 token，id 排在 151643 到 151664：

    id 内容 用途
    151643 <|endoftext|> 文本结束
    151644 <|im_start|> 对话轮次开始
    151645 <|im_end|> 对话轮次结束

    它们不参与字节合并，是整串匹配的固定字符串，反向也直接映射成这串文字。做转换表时要单独处理，否则会当成 BPE token 硬拆成字节。GPT-2 只有一个（<|endoftext|>，id 50256）。

    🧩 id 进 GPU 之后发生什么

    查 embedding 表

    GPU 拿到 id 序列后的第一件事是查表。Qwen2.5-0.5B 的 config 是 vocab_size=151936、hidden_size=896，也就是 151936 行、每行 896 个 bfloat16 数：

    整张表按 bfloat16 算是 259.7 MiB（151936 x 896 x 2 B），比链路上那 76 字节的 id 大了好几个数量级。这一步在实现上是 gather 而不是矩阵乘法：id 就是行号，取哪几行完全由 id 决定，同一个 id 出现两次就取两次。

    对抓包来说这一点值得琢磨：如果能看到显存访问的行地址分布，id 序列基本就暴露了。但链路抓不到显存内部的访问，只能看到进出 GPU 的传输，所以这条路走不通——真正能用的还是本文讲的转换表反查。

    一层 Transformer 里做什么

    embedding 的输出是一张 n_tokens x 896 的矩阵，之后依次穿过 24 层，每一层做的事都一样：

    4864 来自 config 的 intermediate_size，是 FFN 的中间维度，比 896 大五倍多。注意力的两头各要做一次矩阵乘法，FFN 里还有两次，这些就是每层的主要计算量。它们全在显存里完成，链路上看不到中间过程——这正是抓包只能拿到进出的 id、拿不到计算细节的原因。

    注意力在做什么

    注意力的作用是让每个位置的向量去参考其它位置的信息。为了防止模型看到还没生成的 token，计算时会把后面的位置屏蔽掉，每个位置只能看自己和前面的位置：

    # 表示可见，. 表示屏蔽。t1 只能看自己，t5 能看到前面所有位置。这个下三角形状正是 prefill 能一次算完整个 prompt 的原因：每个位置的输出只依赖它前面的输入，所有位置可以并行算；而 decode 阶段新来的 token 依赖已经算完的全部历史，只能一个接一个地来。

    注意力内部会先把每个位置的向量投影成三份：Query（这个位置在找什么）、Key（这个位置有什么特征）、Value（被关注时贡献什么信息），再用 Query 和各个 Key 匹配、按匹配度加权取 Value。所谓 KV cache，缓存的就是每层算好的 Key 和 Value，名字的来源就在这里。

    从 hidden 到 logits，再到下一个 id

    24 层走完，取最后一个位置的向量（1 x 896），过 LM Head 映射到 151936 维。

    Qwen2.5-0.5B 的 config 里写着 tie_word_embeddings = true：这个输出矩阵和输入 embedding 表是同一份权重。模型读问题用的表和写答案用的表是同一张，本文研究的转换表也正是这张表的 id 到字节映射。

    得到的 151936 个数就是 logits，每个候选 token 一个分数，可以是任意实数。中间过一次 softmax 把它变成概率分布，采样器再从分布里挑出一个 id：贪心就是取概率最大的那个；温度（temperature）在 softmax 之前把 logits 除以 T，T 越小分布越尖锐、越确定；top-p 只保留累计概率达到 p 的那几个候选再重新采样。这三个开关只影响选哪个 id，不改变前面任何一步的数据形态。

    生成是自回归的：每产生一个 id 就把它拼回序列，再跑一轮。模型的输出都是这样一 token 一 token 挤出来的，没有一次生成整段的情况。

    prefill 与 decode：两种流量形态

    阶段 算什么 每轮搬多少 id 显存里新增什么
    prefill 一次性处理整段 prompt 一次搬 n 个（prompt 长度） n 个位置的 KV cache
    decode 每次只算一个新 token 每轮 1 个 1 个位置的 KV cache

    两阶段的差别根源在 KV cache：注意力算出来的 K 和 V 可以缓存下来，下一轮直接复用，不必每生成一个 token 就把整段历史重算一遍。代价是显存，Qwen2.5-0.5B 每 token 12.0 KiB（24 层 x 2 x 2 个 KV 头 x 64 维 x 2 字节），4k 上下文约 48 MiB。

    从抓包角度看，这个区别意味着：

    • 权重在模型加载阶段一次性搬完（0.5B 参数按 bfloat16 算约 1 GB），之后推理期不再搬。
    • prompt 的 id 在 prefill 阶段一次性上行，长度就是 token 数乘以每个 id 的字节数。
    • 生成的 id 在 decode 阶段一个个下行。每步回传的是采样后的 id，还是整整 151936 维的 logits（约 600 KB），取决于采样放在哪一侧——放在 GPU 上就只回传 4 字节。
    • KV cache 通常只待在显存里；一旦出现 CPU offload、KV cache swapping 这类显存不够的兜底策略，链路上就会出现周期性的 KV cache 搬运流量。

    📋 三张主要的词表格式

    三种流派

    流派 代表模型 词表文件 空格表示 可逆性
    HF tokenizers Qwen2.5、Llama 3 tokenizer.json（JSON） Ġ（byte-level） 完全可逆
    sentencepiece T5、Llama 2 tokenizer.model（protobuf） ▁（U+2581） 基本可逆
    tiktoken GPT-3.5 / GPT-4 系 .tiktoken（纯文本） Ġ（byte-level） 完全可逆
    WordPiece BERT vocab.txt（纯文本） 空格在切分时就被丢掉，## 前缀表续接 有损

    前面三种都属于子词方案（BPE 或与之相近的 unigram 切分），差别主要在文件格式和空格记号。WordPiece 是另一支，它的 normalizer 常常顺手做小写化、去重音、按标点切分，原文的大小写和空白在编码时就丢了，这类表只能反查出规范化之后的近似文本。

    🎯 落到抓包场景：一串 id 反查文本

    前置假设：链路（PCIe）上传的是整数 id 序列，不是已经渲染好的文本。这个假设待验证，但值得作为基线——如果成立，反查的全部工作量就是本文讲的转换表。

    试解流程

    打分器先只用最朴素的两条规则：越界 id 有几个、解出的文本里有多少替换字符。

    真实试解结果

    • 越界数是最硬的信号。Qwen2.5 的 id 拿去查 GPT-2 表，19 个里有 7 个超出 GPT-2 词表范围，直接排除。
    • 替换字符数是第二硬的信号。GPT-2 的 44 个 id 拿去查 Qwen2.5 表，全部落在范围内，但解出的字节拼不成合法 UTF-8，出现 11 个 �。

    从 DMA 数据里切出 id 序列

    如果链路传的是裸整数数组，切分很直接：

    开头那句 PCIe 链路上抓到的 token id，能还原出原来的问题吗？ 用 Qwen2.5 编码得到 19 个 id，序列化后是 76 字节，开头几个是 c6 d1 00 00 44 00 00 00 d9 46 00 00。但实际抓包更可能遇到：整数混在请求结构体里（带 batch 维度、长度字段、padding），或者一批 id 被拆成多个 DMA 包出现。切分逻辑要按框架的实际结构来，先拿已知文本做一次抓包对照，比盲试靠谱。

    另外，链路如果有加密（PCIe IDE，或 ccAI 那类密文通道），抓到的就是高熵密文，id 结构完全看不出来，得先解决解密或走侧信道的路子——那是另一个话题了。

    ⚠️ 容易踩的坑

    误区 正解
    以为 token 就是词 一个汉字可能占 1～3 个 token，一个英文词可能被切成好几段
    逐个 token 解码再拼字符串 token 边界不在字符边界上，必须先拼字节再做一次 UTF-8 解码
    以为所有模型共用一张表 id 只是行号，Qwen2.5 的 53702 和 GPT-2 的 53702 毫无关系
    把 config.json 的 vocab_size 当词表长度 Qwen2.5-0.5B 的 config 写 151936，tokenizer.json 实际 151665 条
    认为 UTF-8 解得出就是解对了 拿错表也能拼出合法 UTF-8，需要越界数、替换字符、语言模型多层打分
    以为 token 数约等于字符数 同一句中文（PCIe 链路上抓到的 token id，能还原出原来的问题吗？），Qwen2.5 切出 19 个 token，GPT-2 切出 44 个
    忽略特殊 token 它们不在 BPE 表里，<|im_start|> 这类要单独建映射
    只看 id 数值判断模型 词表大小相近的模型会互相吻合一部分，要靠整串打分

    📌 小结

    概念 要点
    切分 byte-level BPE 从 256 个字节起步，按频率合并；中文常被拆到字节级
    id 词表行号，跨模型无语义；同一文本在不同模型下长度差别很大
    GPU 侧 id 查 embedding 变成向量，前向算出 logits，采样得到下一个 id
    两阶段 prefill 一次吃整段 prompt，decode 每步只出一个 id
    解码 id → 字节 → 拼接 → UTF-8，三步顺序不能变
    转换表 id → bytes 的映射；三种格式读进来统一成同一个函数
    反查 多表试解 + 打分（越界、替换字符、可打印比例，必要时加语言模型）

    下一步可以顺着两个方向推进：一是把常见模型的词表都读成同一份 id -> bytes 表结构，用已知文本做一轮往返自测，把转换表这块地基打实；二是把打分器做实，让一串来路不明的整数能自动判出属于哪个模型。抓包侧的前置知识则在《PCIe TLP 解析入门》里。
