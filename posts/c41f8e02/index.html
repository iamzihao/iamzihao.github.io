    Hermes Attack 精读：如何从 PCIe 明文流量里偷走一个 DNN 模型

    Posted on 2026-09-21 Views: Word count in article: 16k Reading time ≈ 29 mins.

    论文：Hermes Attack: Steal DNN Models with Lossless Inference Accuracy（USENIX Security 2021）

    作者：Yuankun Zhu（UT Dallas）、Yueqiang Cheng（Baidu Security）、Husheng Zhou（VMware）、Yantao Lu（Syracuse University）

    概括成一段话：在 CPU 与 GPU 之间那条没有加密的 PCIe 总线上抓包，从 GPU 命令与数据搬运里反推出受害者 DNN 的结构、超参数和全部权重，重建出的模型推理精度与原模型完全一致。

    模型文件放在加密盘里、主机开了 SGX、GPU 也独占不共享，模型文件一个字节都没泄露。但模型仍然可能被整个偷走——Hermes Attack 盯上的不是模型文件，而是模型在 GPU 上跑推理时留下的 PCIe 通信痕迹。

    📚 基本概念速读

    名称 定义 记忆点
    PCIe 主机与 GPU、SSD、网卡之间的高速串行总线 攻击面：明文，可被物理抓包
    TLP Transaction Layer Packet，事务层包 PCIe 上数据传输的基本单位
    Tag TLP 头部字段，请求与回应的配对凭据 用它把 Request 和 Completion 对上
    D command Data movement command，数据搬运命令 权重就是从它的 payload 里捞出来的
    K command Kernel launch command，内核启动命令 决定 GPU 此刻在算哪一层
    KD2D 设备内同步拷贝（也是一条 K command） 参数被复制了一份，追踪必须往回走
    Kernel 编译成 GPU 机器码、在 GPU 上运行的计算程序 每一类 DNN 层对应固定的 kernel
    Architecture 层的数量、类型、维度与连接拓扑 由数据流图恢复
    Hyper-parameters 推理时用到的 kernel size、stride、filters 等 从 K command 参数或 kernel 存在性恢复
    Parameters 训练得到的 weight 与 bias 由 D / KD2D 的数据流恢复

    🎯 起点：模型文件没丢，模型为什么还是丢了

    先把场景摆出来。一家 AI 公司把训练好的 DNN 打包进一台带 GPU 的设备，卖给第三方客户：智能摄像头、车载域控制器、工业质检机，都是这个形态。模型是公司的核心资产，只给使用权，按年收许可费。

    站在模型提供方角度，能做的防护基本都做了：

    • 主机侧：Secure Boot、全盘加密，模型文件本身再用 TEE（比如 Intel SGX）护起来；
    • GPU 侧：不做多租户共享，整块卡只跑自己的任务；
    • 网络侧：设备不出网，模型文件不会被外传。

    这三条都成立，模型文件确实拿不到。但攻击者不需要拿文件——他就在设备现场，可以打开机箱，在 CPU 和 GPU 之间的 PCIe 链路上插一个协议分析仪，把这条链路上跑过的每一个包记下来。

    于是问题变成：

    只看 CPU 与 GPU 之间来回的二进制流量，能不能把整个神经网络扒出来？

    这个问题的答案，就是 Hermes Attack。

    论文的威胁模型（论文 Figure 4）就建立在这条链路上：主机和 GPU 各自都被保护得很好，唯独中间那条 PCIe 是明文，而攻击者能物理接触到它。注意这里没有假设任何软件漏洞——不需要提权，不需要 rooting，不需要攻破 SGX。攻击者拿到的只是一段总线上的流量录音。

    🧭 先分清三个词：结构、超参数、参数

    要偷一个 DNN，得先说清楚偷的是什么。论文把模型拆成三块：

    内容 论文里的叫法 具体指什么
    结构 Architecture 层的数量、每层的类型与维度、层之间的连接拓扑
    超参数 Hyper-parameters 推理时真正用到的那些配置，如 kernel size、stride、filters、pool size、padding
    参数 Parameters 训练得到的 weight 与 bias

    这里有个容易读岔的地方：论文 Background 一节把 learning rate、momentum、epochs、batch size 也算进 hyper-parameters（这是机器学习里的通用定义），但攻击目标里的 hyper-parameters 指的是推理期被用到的那一类，也就是 stride、kernel size、filters。两者不同，前者拿不到，后者能拿到——论文第 3.4.2 节明确说，控制训练过程的超参数无法从推理期流量里恢复。读完后面会更清楚，这个区分决定了 Hermes 的能力边界。

    另一件必须强调的事：论文里的 parameters 专指模型参数（权重与偏置），不是函数参数；kernel 专指 GPU kernel，不是操作系统内核。后文沿用同样的约定。

    🏗️ 模型是怎么跑到 GPU 上的

    一个 DNN 从框架代码到 GPU 硬件，中间要穿过四层软件。这条路径决定了模型信息最后会以什么形式出现在总线上（论文 Figure 1）：

    关键在最后一步：高层计算任务最终都变成了底层的 PCIe 包。反过来说，PCIe 包是这台机器上唯一一份能被外人在旁路完整看到的、与模型执行相关的数据。

    对攻击者来说，这里有个天然的不对称：

    角色 能看到什么
    CPU 侧软件 知道层类型（Conv2D、ReLU、Softmax），但拿不到（攻击者视角下）
    PCIe 总线 只有命令与地址，层类型的语义在 CPU 侧就已经被消掉了
    GPU 侧 只认 kernel 二进制和地址，不知道自己在跑什么网络

    Hermes 要做的，就是把这三份信息缝起来。

    🚧 三个难点

    论文自己列了三条挑战，后面的设计全是为了对付它们：

    1. 闭源与未文档化的数据结构：CUDA runtime、驱动、GPU 内部全是闭源，数据搬运和 kernel 启动涉及的关键结构没有文档；GPU kernel 与 command 还各用一套指令集，反汇编不现实。破解靠的是大量逆向工程。
    2. 语义在 PCIe 层丢失：层类型不会出现在流量里，因为它是在 CPU 侧解析的。少了这个信息，模型只能恢复一半。
    3. 包的噪声与乱序：一次单图推理就能产生上百万个包，论文实测只有 1%～2% 的包对重建有用；而 CUDA 是异步流水线，回应包的到达顺序与它在 DNN 语义上的顺序并不一致。越新的 GPU（例如 RTX 2080 Ti）在这点上越麻烦，因为引入了统一显存与主机内存的新特性。

    📦 第一层：从 PCIe 报文到 GPU Command

    🔗 一次读操作涉及哪两个包

    PCIe 上的通信都以 TLP 为单位。CPU 读外设内存时，链路上会出现两个包（论文 Figure 2、Figure 3）：

    • 读请求包（Memory Read Request）：CPU 发出，指明要读哪个地址，Header 里带 Tag；
    • 回应包（Completion with Data）：外设返回，payload 里就是数据，Header 里的 Tag 与请求包相同。

    Tag 是配对的唯一依据。写操作则简单一些：一个 Memory Write 包，Header 加 payload 就完事。

    论文在流量处理阶段做了一次简化：上游（GPU 到 CPU）只保留 GPU 的读请求包，下游（CPU 到 GPU）只保留回应包，其余类型先丢掉。然后再把同一个 Tag 的请求包与回应包合并成一条 data packet：

    这样每条 data packet 自带了地址和数据，后面的分析只需要面对这一种结构。

    🧵 为什么要 Merge 和 Sort

    PCIe 协议不保证多个连续请求的回应顺序，一次读请求的结果还可能被拆进多个回应包里。所以抓到的原始顺序不能直接用，Hermes 用两步修正：

    合并（Merge）：按 Tag 找到请求包对应的所有回应包，补全 Tag 字段，相邻的同 Tag 包拼成一个包，payload 顺次连接。

    排序（Sort）（论文 Figure 6）：

    1. 默认所有包按 packet ID 从小到大排列；
    2. 取一个请求包记为 P1，向后找第一个 Tag 与它相同的包，记为 P2；
    3. 在与 P2 相同 packet ID 的 data packet 里找到 P3；
    4. 把 P1 的 packet ID 写进 P3 作为排序键；
    5. 重复直到所有 data packet 都有排序键，最后按排序键重排。

    这一步是后面所有分析的地基：排序键的顺序，就是 GPU 执行 DNN 的顺序。

    ⌨️ D Command 与 K Command

    GPU 命令也由两部分组成：Header 说明这是什么命令、数据有多长；Data 是命令携带的值。论文把所有命令归成两类，只关心这两类：

    命令 含义 论文中的变体 用途
    D command 数据搬运 D、KD2D、Dasyn 传输入、传中间结果，也传权重
    K command 启动 GPU kernel K、KD2D 决定 GPU 在跑哪个 kernel，也就是哪一层

    注意 KD2D 两边都沾：它是启动一个做设备内拷贝的 kernel，所以既是 K command 的一种，行为上又是数据搬运。

    🔍 离线摸清 Command Header

    要按类型过滤命令，就得知道 Header 长什么样，而 GPU 的命令格式没有文档。论文的办法是离线构造实验做差分，思路很朴素：只改一个变量，看哪个字段跟着变。

    • 摸 D command：反复在预分配的显存和主存之间搬运构造好的数据，对抓到的包做模式匹配。
    • 摸 K command：反复用准备好的参数启动 kernel，比对包的变化。

    最后得到一条命令的 Header 是 9 个 DW（Double Word，4 字节），其中三个字段最有用：

    • DW3：这条命令在 GPU 内存里的地址。
    • DW5：数据段的字节数。
    • DW9：命令类型，例如 6D204860 是 Kepler 架构上 kernel launch 的签名（论文把签名对应的位级语义引向了 Envytools 的逆向工作）。

    论文还做了穷举测试，确认 Header 结构在不同 GPU 与整机组合上稳定可用，并把结果存进 profiling 数据库，后续分析直接查表。

    🧹 噪声过滤：物理地址不连续怎么办

    按 Header 过滤出 D / K command 之后，每条命令的 payload 仍然混着噪声。论文把它们分成两类：

    • 外部噪声（external noise）：不属于当前命令的包。一条数据量大的命令要几千个包才传完，中间很容易插进别的命令；更麻烦的是命令 Header 自己可能被拆进两个包，噪声包就卡在中间。
    • 内部噪声（internal noise）：包内某个固定 DW 位置上的干扰字段。论文把这类模式全部列了出来，抽取 payload 时直接剔除。

    最直觉的过滤方法是检查地址连续性——同一命令的数据在内存里通常连续。但这招不完全可靠：包里的地址是物理地址，CUDA 程序用的虚拟连续空间可能被切成多段物理内存，相邻两个包地址不连续是正常的；反过来，一条命令的数据太大时也会跨越多个物理块。

    🧩 第二层：从 GPU Kernel 到 DNN Layer

    层类型在 CPU 侧就被解析掉了，PCIe 上根本没有这个信息。Hermes 靠一个关键观察把语义补回来：每一类 DNN 层，最终都对应着一批固定的 GPU kernel 二进制。

    🧱 Kernel 是什么，怎么进到 GPU

    nvcc 把 kernel 编译成硬件相关的可执行代码（CUDA Fatbin），嵌在宿主可执行文件的专用 section 里（例如 libcudnn.so 的 nv_fatbin）。运行到某次调用时，这段二进制被搬到显存里，再被启动执行。

    这里有一个很好用的性质：大家都倾向用厂商高度优化的标准库（cuDNN、Eigen），所以kernel 二进制相对稳定。比如卷积层调用 cudnn::detail::implicit_convolve_sgemm，这段二进制就躺在 libcudnn.so 里。二进制稳定，意味着离线阶段建立的那张对照表可以反复使用。

    🔎 两条观察，一个反向定位

    论文给出两条观察：

    观察 1：每个 kernel 是通过一条 D command 加载到 GPU 上的，这条 D command 的数据段就是 kernel 二进制。

    观察 2：每条 K command 里都有一个地址，指向将要启动的 kernel 二进制。

    💰 第三层：把 Weight 和 Bias 取出来

    结构与超参数有了，还差参数。参数和前面几样不同——它是明文搬到 GPU 上的，所以从数据搬运命令里就能直接读到数值。难度在于：D command 不只搬参数，还搬输入、搬中间结果，怎么把参数挑出来。

    ❓为什么不能把 D command 的数据全当权重

    一个自然的想法是：把所有 D command 的 payload 都当作候选参数，逐一验证。但这行不通，因为大量 K command 压根不用 D command 搬来的数据，它们用的是别的 K command 新造出来的地址。跟 CUDA trace 对齐后，论文发现这些 K command 在做设备内存到设备内存的拷贝，于是给出第三条观察：

    观察 3：CUDA 会用 K command 做设备内的同步拷贝，论文称之为 KD2D。DNN 参数由 D command 送进 GPU 后，经常被 KD2D 再复制一份，真正参与层计算的是那份副本，原址的数据保持不动。

    为什么要有这份副本？论文的解释是：设备内拷贝用 kernel 比用 D command（受 DMA 控制）高效得多；而保留原址是为了避免推理过程中原始权重被覆盖污染。

    这条观察直接决定了恢复参数的路径：参数被复制过，就必须从使用方往回追，追到最初的来源。

    🧱 拼装：从数据流图恢复完整模型

    到这里，单条命令、单个 kernel、单块参数都能解读了。最后一步是把碎片拼成模型。

    🕸️ Kernel 是顶点，数据搬运是边

    论文的重建思路是把 DNN 的执行看成一个数据流图（data flow graph）：

    • 每次 kernel 启动 = 一个顶点；
    • 每次数据搬运 = 一条边。

    每个 kernel 至少读一个地址、写一个或多个地址。至于哪几个偏移是输入、哪几个是输出，靠离线阶段 profile 好的语义（K command 里输入输出地址的偏移）来判断。按输入地址连出、输出地址连入，图就建起来了。

    有个细节不能想当然：一个 kernel 的输出地址未必等于后继 kernel 的输入地址。两个地址可能落在同一个数据块里，也可能中间隔了一次 D command 拷贝。所以建图时要迭代 D command 来确认地址之间的传递关系。论文提到 SwapDimension1And2InTensor3UsingTiles 这个 kernel 就要专门记录，因为它参与了数据流的走向恢复。

    图建好之后，把每个顶点替换成查表得到的层类型，Architecture 就出来了。

    🧾 超参数的两条恢复路径

    推理期用到的超参数，来源只有两种：

    来源 例子 做法
    K command 的参数 stride、kernel size、filters、pool size 按离线 profile 出的偏移，从 kernel 的 K command 数据段里取值
    某个 kernel 是否出现 use_bias 这类布尔量 例如出现 BiasNCHWKernel，就判定这一层用了 bias

    论文 Table 3 给出了一张偏移表，摘录卷积层部分（偏移指 K command 数据段里，从第一个 word 到目标超参数的距离，以 word 计）：

    超参数 主 kernel 编号 GT 730 1080 Ti 2080 Ti

    Strides 2 126, 127 123, 124 120, 121

    这张表值得多看一眼：同一批超参数在不同 GPU 上的偏移并不相同，同一层在不同实现下还可能对应不同的 kernel。所以离线阶段必须换平台重做，数据库是按平台建立的，不能跨代套用。

    ➕ ResNet 的 shortcut 怎么恢复

    前面都是链式结构，ResNet 不一样——它有 shortcut，同一份数据会被主干之外的路径再用一次：

    在 PCIe 层看不到任何叫 shortcut 的东西，但数据流图会暴露它：同一个地址被多个 kernel 当作输入，或者某个地址上出现显式的加法 kernel（Eigen::internal::scalar_sum_op），这就是分支与汇合的痕迹。恢复出来的顶点与边只要忠实反映数据依赖，分支结构自然就出来了。

    这也是显存地址在 Hermes 里如此重要的原因：层与层的连接关系不在命令里，而在地址的流向里。

    🧮 重建结果与原模型的两处差异

    论文用 Figure 12 对比了三个模型的原始结构与重建结构，结论是语义等价，有两处形式上的差异：

    • 重建模型没有 dropout 层（MNIST、VGG 上可见）。dropout 只在训练期生效，推理时被禁用，所以它根本不会在 PCIe 上留下痕迹；也正因为推理时不起作用，缺了它不影响推理结果。
    • 重建模型把每个激活函数当成独立的一层（MNIST、ResNet 上可见）。这是实现风格差异：有的模型把激活函数写成层的超参数，有的写成单独的层。论文统一按独立层处理，同样不带来精度差异。

    • 受害者模型：MNIST、VGG16、ResNet20，用 Keras 加 TensorFlow 后端跑推理，实验中被当作黑盒，只用于事后核对。

    📌 Lossless 的含义

    标题里的 Lossless 容易被误读成 PCIe 数据无损，实际上论文指的是：

    重建出来的模型，推理精度与原模型一字不差；与原模型精度高不高无关。

    论文第 5 节开头把这一点说得很直白：无论受害者模型精度如何，重建模型都与它一致；激活函数的数量、模型层数也不会影响攻击的成功。这比早期的模型抽取工作强一个量级——那些工作在预测式攻击下精度会掉，在搜索式攻击下拿不到定制模型，而且都只能恢复模型的一部分。

    🚧 边界：Hermes 做不到什么

    精读不能只写攻击有多强，还要写它的前提与天花板。论文自己讨论了这些限制。

    🚫 训练期的信息拿不到

    Hermes 是推理期攻击，只看到一次推理的流量。所以：

    信息 能否恢复 原因
    训练超参数（learning rate、momentum、epochs、batch size、正则项） 否 只出现在训练过程，不出现在推理流量里
    dropout 层 否 推理时被禁用，不产生流量
    结构与推理用超参数 能 数据流图 + K command 参数
    weight 与 bias 能 D / KD2D 的数据搬运

    换句话说，攻击者拿到的是一个能直接部署、精度一致的推理模型，而不是一份能继续训练的完整训练配置。

    💾 超大模型与抓包 buffer

    抓包设备的 buffer 是硬限制。论文用的分析仪 8GB（每方向 4GB），面对 ImageNet 上训练的 VGG16 就不够用了：模型本身约 500MB，但 PCIe 与 GPU 产生的大量元数据会把下游流量顶过 buffer 上限。

    两个出路：

    • 换设备：例如 Summit T34 可把 buffer 扩到 64GB，理论上能装下现有 DNN 的推理流量；
    • 分段恢复：先抓前 n 层，下次跳过 k 层再抓（k ≤ n），重复到最后一层，最后把各次恢复的层拼起来。这条路不依赖新硬件，但要求拦截窗口切得准，而且要有只有部分层数据时的恢复能力。

    🖥️ 平台、框架与多任务

    变量 影响 应对
    换 GPU 型号 command header 结构可能变、指令集变导致 kernel 二进制变 用离线阶段的方法重新摸 header、重建数据库
    换 DNN 框架 每层的实现与 kernel 的对应关系会变 只要层都在 GPU 上执行，重新建立层与 kernel 的映射即可
    换 NPU 等加速器 底层机制不同 论文认为 PCIe 与 GPU 的工作机制不变，攻击思路可迁移
    同卡多任务 别的任务的数据会混进来 每个进程有独立的 GPU context，每个 context 至少一条 channel 发命令，按 context 过滤

    🧱 攻击成立的前提

    把前提一次性列清楚：

    1. 攻击者能物理接触设备，并能在 CPU 与 GPU 之间插入抓包设备；
    2. 这条 PCIe 链路没有加密；
    3. 攻击者能在同型号平台上跑离线 profiling（为白盒模型建立对照数据库）；
    4. 目标模型的各层都在 GPU 上执行（论文假设如此；若某些层被搬到 CPU，那些层就不会出现在流量里）；
    5. 抓包设备能完整记录一次推理的流量（受 buffer 限制）。

    缺任何一条，攻击要么失败、要么只能恢复部分模型。

    🛡️ 论文提出的缓解思路

    论文第 5.3 节列了几条对策，也顺带说明了各自的问题：

    缓解手段 思路 局限
    PCIe 加密 在链路上加密码引擎，让抓包拿到密文 CPU 侧加容易，商用 GPU 普遍没有这个能力；缺少向后兼容
    数据混淆 混淆命令、模型命令与参数 需要扩展 kernel 来反混淆，只能抬高门槛，无法完全阻止
    软件侧噪声注入 一个进程发数据、另一个进程发干扰命令 可用 GPU channel 与 context 过滤掉
    动态 command header 由驱动动态生成 header，而不是固定结构 显著提高逆向成本，但仍是提高门槛
    把部分任务卸载到 CPU 减少 PCIe 上暴露的信息 CPU 算力远低于 GPU，频繁来回搬运会带来明显性能损失

    值得注意的是，这些手段里只有链路加密真正从根上解决问题，而它对商业 GPU 的兼容性最差。这也解释了论文的立场：在明文 PCIe 仍是常态的部署环境里，模型资产实际比人们以为的更脆弱。

    🧠 我的理解：Hermes 利用的是语义泄漏

    读完这篇论文，我觉得它最值得记住的不是某个具体技巧，而是它把一次攻击拆成了三层语义还原。每一层解决一个不同的问题：

    层次 输入到输出 回答的问题
    报文层 TLP → D / K command 这串二进制是什么？（Merge + Sort + Header）
    命令层 D / K command → kernel → layer GPU 在做什么？（kernel 二进制 ↔︎ 层类型）
    语义层 地址与数据 → 参数与拓扑 这些行为在 DNN 里意味着什么？（数据流图 + 反推参数）

    三层里，第一层靠的是协议知识（PCIe 规范是公开的），第三层靠的是数据依赖推理（地址流向），最难的是中间那层——GPU 命令格式没有文档，层类型在总线上不存在，这两件事只能靠离线差分实验和一张对照表硬啃下来。

    论文里几个设计我印象比较深：

    • 用离线阶段换在线阶段的可行性。 闭源逆向的结果被固化进数据库，在线阶段只做查表与重建，所以单张图片、十几分钟就能出完整模型。攻击的可扩展性其实来自这次成本转移。
    • 每一条观察都直接对应一个实现难点。 观察 1、2 解决 kernel 语义缺失，观察 3 解决参数被复制的问题。这种从观察直接落到机制的写法，读起来很顺。
    • 用 Header 声明的数据大小当抽取终止条件。 物理地址碎片、命令交错、异步传输这些噪声都很脏，但只有一个明确的收敛条件，工程上才做得稳。
    • 术语上的小心。 论文把训练超参数与推理超参数都叫 hyper-parameters，但在攻击目标里只谈后者。这个区分看着琐碎，却正好划出了攻击的能力边界。

    最后一点感受：Hermes 提醒我们，模型资产的安全性并不只取决于模型文件本身，还取决于它在执行过程中向外泄漏了什么。这次泄漏的通道是明文 PCIe；只要加速器与主机之间还有未加密的高速链路，同类问题就还会以别的形式出现。

    ✅ 总结

    Hermes Attack 用离线逆向换来的知识，把一次推理的明文 PCIe 流量还原成完整 DNN：命令 header 认路，kernel 二进制认层，数据流图认结构，地址追踪认权重。

    留一个要点：层与层的连接关系不在命令里，而在显存地址的流向里。

    对防御方的启示也很直接：模型文件加密、主机开 SGX、GPU 独占，这些都不能替代链路加密——只要 CPU 与 GPU 之间还在传明文，模型就仍然暴露在一个可以被旁路监听的位置上。
