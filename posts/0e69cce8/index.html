Rust OS 前置：逐行拆解 VGA 的 Writer

Posted on 2026-09-07 Edited on 2026-09-10 Views: Word count in article: 8.3k Reading time ≈ 15 mins.

前三篇的语法与思想，最终都落在一个真实的模块上：VGA 文本模式的 vga_buffer.rs。这篇不贴全文，而是把它拆成九块来读——从颜色怎么压进一个字节，一直讲到 println! 怎么变成对显存的一次写。

前置阅读：《从 C 到 Rust》《借用与生命周期》《属性与内存布局》，以及《Rust OS 入门：VGA 字符模式》。

📚 素材速读

要拆的部件和它们所属的层：

部件 职责 对应层
Color / ColorCode 16 色编号，以及把前景与背景压进一个字节 第一层
ScreenChar 一个屏幕格子：字符 + 颜色 第二层
Buffer 25 × 80 个格子，映射到 0xb8000 第二层
Writer 记录当前写到哪一列、用什么颜色，对外提供写屏接口 第三层
write_byte / new_line / clear_row 写一个字符、屏幕上滚一行、清空一行 第四、五层
write_string 把 &str 拆成字节逐个写出 第六层
fmt::Write 让 Writer 接进 Rust 的格式化体系 第七层
WRITER 全局唯一的 Mutex<Writer> 第八层
print! / println! 提供给内核其余部分使用的打印宏 第九层

🎨 第一层：Color 与 ColorCode——颜色怎么压进一个字节

#[repr(u8)] 是这里的枢纽：没有它，枚举的底层类型不由你决定，Color::Yellow as u8 拿到的值也不可控。ColorCode 那层包装解决另一个问题——给一个字节起个有语义的名字，同时靠 #[repr(transparent)] 保证它真的还只是一个字节，能直接塞进下一层的 struct 里。

🧱 第二层：ScreenChar 与 Buffer——一个格子与整块屏幕

Volatile 是这一层唯一需要展开的地方。显存是内存映射 I/O（MMIO），它的内容会被硬件改动，而编译器看不到这件事；没有这层包装，编译器可能把连续的多次写合并掉，也可能认为刚写进去的值还在寄存器里、读取时不必回内存。第五层的 new_line 要整行读出来再写回去，正是这种读写都必须真的落在内存上的场景。Volatile<T> 自身也是 #[repr(transparent)] 包装，所以 Buffer 在内存里仍然严格是 25 × 80 × 2 字节，和显存逐格对应。

前面几篇为了讲语法，把 Buffer 写成 [[ScreenChar; 80]; 25] 并加了 #[repr(transparent)]。真实代码里 Buffer 没有任何属性，元素是 Volatile<ScreenChar>；真正需要 #[repr(transparent)] 的是第一层那个 ColorCode。

🖋️ 第三层：Writer——写字的人

三个字段凑起来就是一句话：光标在哪、用什么颜色、往哪写。后面所有方法都只是围绕这三件事操作。

✍️ 第四层：write_byte——往显存写一个字符

&mut self 是必需的：写一个字符要同时改 column_position 和显存内容，属于可变借用（篇二）。另外留意 row 固定取最后一行——这一版实现里光标不高亮也不移动，始终停在末行，写满一行就把整屏上滚，这也是第五层存在的理由。

📜 第五层：new_line 与 clear_row——屏幕滚动

这段的语义是 把显存里的内容搬到显存里的另一个位置，所以它必须用 volatile 读写：只要中间某次读被缓存进寄存器，搬过去的就可能是旧值。另外这两个方法都没有 pub，滚动和清行是内部细节，只由 write_byte 调用（篇一：pub、私有）。

🔤 第六层：write_string——从字符串到字节

0x20..=0x7e 是可打印 ASCII（空格到 ~），加上换行符，这两类原样写屏；其余字节统一写成 0xfe，而它在 VGA 字体里是实心方块。中文每个字 3 个字节且都大于 0x7e，所以走的是这一路——屏幕上一串方块字的来历，也是这套 VGA 打印只适合英文的原因。

🖨️ 第七层：fmt::Write——接进格式化体系

fmt::Write 是格式化输出的标准 trait，必须实现的只有 write_str，其余（write_fmt、write_char）都有默认实现。真正解析 {} 占位符的 write_fmt 就是默认实现：它把格式串拆成一段段文本，再交给 write_str。

另外注意 use core::fmt; 写在文件中部。Rust 的 use 可以出现在模块里的任何位置，作用范围都是整个模块，不必集中到文件开头——这一篇里几个 use 就散落在各自用到处。

🌍 第八层：lazy_static 与 Mutex——全局唯一的 WRITER

这里要回答两个设计问题：

  • 为什么不是普通 static：static 的初值必须在编译期算出来，而这里要做整数到指针的转换、解引用裸指针，还要构造 Mutex（这时候的 spin::Mutex::new 不是 const fn）。lazy_static! 把它变成惰性初始化：第一次访问 WRITER 时构造一次。它在 Cargo.toml 里开了 spin_no_std feature——惰性初始化本身需要一把锁保证只初始化一次，而裸机环境没有 std 的 Once。
  • 为什么外面还套 Mutex：buffer 是 &'static mut，可变引用不允许有别名。自旋锁把对 Writer 的访问串起来，同一时刻只有一个持有者；spin::Mutex 不依赖操作系统，适合 no_std，而 std::sync::Mutex 需要系统调用。

组合起来，unsafe { &mut *(0xb8000 as *mut Buffer) } 的意思是：

通过裸指针找到那块显存，把它借成一个可修改的 Rust 引用，交给 Writer 使用。

套 unsafe 是因为编译器无法证明 0xb8000 处真的有一个合法的 Buffer——这是硬件规定的事实，由程序员负责声明。unsafe 只把这道门打开一条缝：&mut 拿到手之后，后续操作仍受类型系统与借用检查约束（篇二）。同一个 unsafe 块还隐含另一个承诺：这块显存只会经由这一个引用访问，不会同时造出别名——这正是它被放进 Mutex 的原因。另外，这个地址能直接解引用，是因为此时 bootloader 已经做好分页映射，让这个虚拟地址正对着物理显存。

🔗 第九层：print! 与 println!——宏与 _print

四点机制值得留意：

  • macro_rules! 匹配的是语法片段而不是值，$($arg:tt)* 表示任意多个 token tree。所以 println!("{} {}", a, b) 这类展开只有宏能做到，普通函数不行。
  • format_args! 是编译器内置宏：原地构造一个 fmt::Arguments，只记录格式串和各个参数的位置，全程不分配内存，正好适合 no_std 内核。
  • $crate 指回定义宏的那个 crate。宏 #[macro_export] 导出后可能在别的 crate 里展开，那时写死 crate::vga_buffer::_print 会解析到调用方去，用 $crate 才能保证路径总是指回这里。
  • println! 的两条规则按顺序匹配，所以不会打架；_print 里 WRITER.lock() 拿到的 MutexGuard 把格式串一路拆到 write_str，锁在语句结束时自动释放。

🧅 学习方法：Rust 代码可以剥洋葱

看到类似的表达式不要当成一整坨语法，而是从右往左一层层拆：

Rust 代码几乎都可以这样拆开读。学 Rust OS 时，最值得先打通的主线就一条：

对象 → 所有权 → 引用 → 借用 → &mut → 裸指针 → unsafe → 生命周期

这条线弄明白后，后面 Writer、Volatile、lazy_static!、spin::Mutex、中断处理这些模块，基本都围绕同一套思想展开——只是包装越来越厚。这篇文章从第一层拆到第九层也是同一个道理：每一层单独看都不难，难的是把它们串成一条从 println! 到显存的通路。

✅ 总结

VGA 的 Writer 把前三篇的语法串成了一条完整链路：repr(u8) 的 Color 与 newtype ColorCode 把颜色压进一个字节 → repr(C) 的 ScreenChar 描述一个格子 → Volatile 包装的 Buffer 描述整块显存 → 整数地址经 as 变裸指针 → unsafe 加解引用变成 &'static mut 引用 → spin::Mutex 与 lazy_static! 把它变成全局唯一实例 → fmt::Write、print!、println! 一层层包装成安全接口。读这类代码的关键是剥洋葱：一层层拆开看每一步做了什么。

Happy Hacking! 🎉
