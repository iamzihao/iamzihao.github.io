    IKnowWhatYouSaid 精读：从 CPU 缓存里读出本地 LLM 的输入与输出

    Posted on 2026-09-24 Views: Word count in article: 12k Reading time ≈ 22 mins.

    论文：I Know What You Said: Unveiling Hardware Cache Side-Channels in Local Large Language Model Inference（USENIX Security 2025）

    作者：Zibo Gao、Junjie Hu、Feng Guo、Yixin Zhang、Yinglong Han、Siyuan Liu、Haiyang Li、Zhiqiang Lv（中国科学院信息工程研究所、中国科学院大学网络空间安全学院）

    概括成一段话：把 LLM 部署到本地并不等于对话内容留在本地——同一台机器上一个没有特权的普通应用，只要盯住 CPU 缓存的访问模式和自回归解码的时序，就能把这次推理的输入与输出文本还原出来。

    本地部署 LLM 的出发点是把数据留在自己机器上：不发给第三方 API，隐私敏感的内容不出门。这篇论文指出的是另一条路径——机器内部还有一条不属于软件层的泄漏通道。token embedding 查表时的访存模式泄漏了 token 的值，解码阶段每个 token 的时间点泄漏了 token 的顺序，两者都落在硬件缓存上。攻击者不与 LLM 进程交互，也不需要任何特权，用一个普通应用在后台记录缓存访问即可。

    📚 基本概念速读

    名称 定义 记忆点
    Token embedding 把 token id 映射成稠密向量的操作 泄漏源头：查了哪一行就暴露了哪个 token
    Embedding table 形状为词表大小 × 向量维度的参数矩阵 攻击者只需知道它在模型文件里的偏移
    Prefill 一次吃完所有输入 token、并行计算的阶段 缓存命中事件密集，切分靠它
    Decode 自回归逐 token 生成的阶段 一次一个 token，时序规律
    TPOT Time Per Output Token，生成一个 token 的耗时 决定时序信号的主频
    flush+reload 共享内存下的缓存侧信道原语 探针精度到缓存行，能分辨 embedding table 的每一行
    Cache trace 攻击者采到的 时间 × 地址 延迟矩阵 攻击的全部原始素材
    False positive / negative 多检（没访问却报命中）/ 漏检（访问了没报） 噪声的两个来源
    PSD Power Spectral Density，功率谱密度 用来看 decode 阶段时序信号的周期性
    zero-copy 加载 框架用 mmap 直接映射模型文件、省掉一次拷贝 顺手给了攻击者一份共享内存
    ASR Attack Success Rate，本论文定义为语义相似度大于 0.77 的样本比例 阈值来自 100 人的人工投票

    🎬 起点：模型留在本地，对话为什么还是漏了

    先看场景。用户在自己的 PC 上跑一个本地 LLM：llama.cpp、Ollama、GPT4All 这类框架都算，模型是常见的小尺寸量化版本，日常用来问私事、写敏感邮件。机器上还装了别的东西，其中一个是攻击者放出来的普通应用——它可能就挂在应用商店里，行为完全合法。

    论文的威胁模型建立在这三条假设上：

    1. 攻击者没有特权：只是一个能与受害者同时运行的进程，操作系统隔离照常生效，不改 LLM 用的任何库，不与 LLM 进程通信；
    2. 攻击者只需要几条常规能力：能执行代码，能以只读方式打开模型文件并 mmap（拿不到就退而用操作系统的页去重拿到共享内存），能执行 clflush 清缓存；
    3. 攻击者不需要知道模型结构，也不需要框架的源码或二进制，但能根据公开的模型文件格式（safetensors、pickle）算出 embedding table 的地址偏移。

    图里最关键的一点是不对称：进程隔离挡住了直接读内存，但挡不住共享的缓存。这张表在物理内存里只有一份，两个进程各自的页表都指向它，缓存行的命中与否对所有核都是同一个事实。

    🔑 前提：embedding 查表跑在 CPU 上

    这条假设决定了攻击能不能成立，论文也专门做了说明：token embedding 这一步在 CPU 上执行，模型其余各层可以放在任何设备上（包括 GPU）。

    理由是成本。本地部署里 CPU 做 embedding 最划算，Intel 的 CPU 推理白皮书、Meta 的 Llama Everywhere、Numenta 以及各个社区框架都把 embedding 留在 CPU，只把后面的矩阵计算丢给 GPU。所以一份跑在 RTX 3060 上的 llama.cpp，它的 embedding 查找依然发生在 CPU 上。

    反过来说，一旦 embedding 也被放到 GPU 上查表，CPU 的缓存攻击就看不到了：离散 GPU 的缓存与 CPU 缓存不保持一致。论文的框架评估里唯一失败的 GPU 配置，正是这个原因（见后文）。

    🔍 两条泄漏源：token 值与时序

    🎯 泄漏一：查表模式暴露 token 值

    LLM 的输入输出都是 token 序列，模型需要先把每个 token 变成稠密向量才能计算，这一步叫 token embedding。写成矩阵形式，就是对 one-hot 编码做一次线性投影：

    one-hot 是稀疏的，所以实现上没人真的做矩阵乘法，而是退化成一次查表：取 W 的第 ti 行。而查表是访存行为，访存会经过缓存：

    第 i 行被载入缓存这件事，在缓存侧信道上可以直接观察。于是观察到哪一行命中，就反推出此刻处理的是哪个 token。

    还有一步放大：LLM 是自回归的，新生成的 token 会被重新喂回模型，再次经过 embedding。所以这一条泄漏同时覆盖输入 token 和输出 token——用户问了什么、模型答了什么，都会在同一个表上留下痕迹。

    ⏱️ 泄漏二：自回归时序暴露 token 顺序

    知道有哪些 token 还不够，还需要知道它们的顺序。论文在时间维度上另找了一处泄漏：LLM 推理分 prefill 与 decode 两个阶段，prefill 先把全部输入 token 算完，decode 再一个 token 一个 token 地往外吐。这些阶段天然串行，decode 要等 prefill 结束，第 i+1 个 decode 要等第 i 个 token 出来。

    于是时间轴上能得到两件事：

    • 输入与输出的分界：prefill 结束的时间点，就是模型开始回答的时间点；
    • 输出 token 的顺序：每个 decode 阶段对应一个 token，先后顺序就是文本顺序。

    🚧 两个真正的难题

    论文自己列了两条挑战，后面所有设计都是围着它们转：

    挑战 现象 后果
    C1 噪声 缓存侧信道有假阳性与假阴性 token 列表里混进随机 token、丢掉真 token
    C2 输入顺序被打乱 prefill 把输入 token 批量并行计算，embedding 操作在时间轴上交叉重叠 输入 token 被还原成一个无序集合，顺序丢了

    C1 的解法是引入一个微调过的 LLM 去噪，C2 的解法是利用输入与输出的上下文关联给无序 token 排序。这两个模型在论文里叫 LLMA 与 LLMB。

    🧩 攻击总览：五步把缓存轨迹变成文本

    前 3 步是信号处理，后 2 步是模型推理。这种分工也解释了论文的方法论取向：硬件侧只负责拿到质量不高的观测，语义层的补全交给自然语言模型去做。

    每个 i 只挑一个确定地址作为探针。论文提到，攻击者并不需要模型或框架的任何秘密，这些偏移都能从公开的文件格式文档里推出来——safetensors 与 pickle 的格式是公开的，主流 LLM 的 embedding 位置也遵循同样的规则。

    🤝 共享内存从哪来

    缓存攻击要求攻击者与受害者共享物理内存。论文用了两条互相替代的路径：

    • 首选 mmap：现在主流的 LLM 框架都用 zero-copy 方式加载模型，直接把模型文件映射进地址空间、按需分页。攻击者对同一个模型文件调一次 mmap，两个进程就会因为 page cache 落在同一批物理页上，共享内存是白送的，不需要页去重；
    • 备选页去重：万一某些框架不支持 zero-copy，就用操作系统提供的 page deduplication（KSM 一类机制）拿到共享页。

    这里的因果关系值得留意：zero-copy 是一个性能优化，它顺手把攻击面也一起送了出去。论文后面给出的对策之一，正是把它关掉。

    ⚠️ 硬件预取器把标准 flush+reload 打趴了

    论文里值得一提的一段，是它报告了一个负面结果。

    按标准做法实现 flush+reload 之后，攻击在 Intel 的 Raptor Lake（13 代酷睿）上几乎完全失效：监视 32768 个地址（Llama 2 的词表大小）时平均每秒 5,612,394 次假阳性，精度接近零。

    原因是硬件里的 AoP 预取器（Array-of-Pointers prefetcher）。为了对抗流式与空间预取器，标准实现会把目标地址打乱后放进一个指针数组；而 AoP 预取器的行为恰恰是解引用数组里的指针，于是探针数组一被访问，几乎每个目标地址都被预取进缓存，全部看起来像命中。

    绕过办法很朴素，却正好卡在预取器的语义上：

    数组里只存偏移（每个目标地址减去最小地址），访问时再把偏移加回去还原真实地址。这样数组里没有任何合法指针，AoP 预取器无事可做。其余的预取器沿用前人的做法对付：探针地址不落在相邻页上、访问顺序随机化。

    🖥️ 缓存轨迹长什么样

    采集结果是矩阵 o：L 个时间点 × |V| 个目标地址的访存延迟，另外用 rdtsc 记下每个时间点的物理时间戳。论文用一幅热力图（Figure 3）展示它：颜色越深表示该行越可能被访问。在这样一张图里，prefill 表现为一条竖直的密集色带，decode 表现为稀疏的散点。

    实现上，论文把探针线程分成 15 个分区（partition），每轮按伪随机顺序扫自己那一份地址（s = t*m + (v*167 + 13) % n），并在每个内存页取中间地址作为探针，尽量避开相邻页带来的预取噪声。

    ✂️ 切段与映射：prefill 在哪，decode 在哪

    攻击者不与 LLM 交互，所以不知道推理是什么时候开始的——这属于经典的异步攻击场景。论文用一个模式匹配算法在轨迹里找两个阶段的起点：

    • prefill 起点：从某个时间点起，连续不少于 K 个事件的时间间隔都小于阈值 α1。输入是批量并行计算的，命中事件会异常密集地挤在一小段时间里；
    • decode 起点：在 prefill 之后，出现至少一个间隔大于 α1 的事件。decode 一次只产出一个 token，事件稀疏得多。

    论文的取值是 K = 4（允许的最小输入 token 数）与 α1 = 10⁻³（不大于一次前向传播的最小耗时）。

    切完之后，轨迹被映射成三样东西：

    输出 含义 怎么得到
    KD 有序 token 列表（decode 段） 每个时间点命中哪些地址，查表反查成 token 文本，去掉空集
    TD 时序信号（decode 段） 每个命中事件对应的时间戳序列
    KP 无序 token 集合（prefill 段） 整个 prefill 段命中的地址并起来反查

    判定的细节是缓存命中阈值 α2：延迟低于 α2 记为命中，α2 来自缓存微基准测试。到这里，硬件侧的工作就结束了，剩下的是从一个很脏的 token 列表和一条带噪的时间戳序列里把文本拼回来。

    🧠 去噪与还原输出：LLMA 与时序信号

    📈 为什么自回归会产生周期性

    论文的出发点是两条观察：

    1. 自回归生成是数据流驱动的，前向传播走的是规整的流水线，不同于控制流驱动的程序；
    2. 于是每次生成 token 可以近似看成周期性事件。

    周期有多长？就是 TPOT。论文在 13900K + RTX 3060 上跑 Phi-3.5-mini（llama.cpp），预期在 100Hz 处出现峰，也就是每 10 毫秒生成一个 token（原文这一句把 TPOT 写成约 10 microseconds，按 100Hz 反推单位应是 ms，见文末口径一节）。用傅里叶变换把时序信号转到频域、算功率谱密度（PSD）：

    真阳性（真的由 embedding 造成的命中）在 PSD 上给出基频与谐波，是清晰的峰；假阳性则频谱平坦、接近白噪声。这个差别就是去噪的立足点。

    📉 一阶差分：峰是漏检，谷是多检

    PSD 只能证明信号有周期性，不能直接指出哪个时间点是噪声。论文的做法是先把周期成分减掉：用 SWIPE’ 算法从 PSD 里估出基频 f0，再算归一化一阶差分。

    理想情况下，相邻两次真命中的间隔是 T，所以差分应该稳定在 f0 · T。偏离这个基准的两类异常正好对应两类噪声：

    • 峰（间隔接近 2T）：中间少了一个事件，也就是漏检。真阳性原本应该在 t1 与 t2 之间出现，把它的缺失补回来——预测这个位置的 token 并插进 KD，相当于做完形填空；
    • 谷（间隔明显小于 T）：多出来一个事件，也就是多检。把它从 KD 里删掉。

    论文把这三选一（补一个、删一个、不动）统一写成序列到序列任务：

    由微调过的 LLMA 实现：输入是时序信号与 token 列表的交替序列，输出是清理后的文本。微调用 LoRA，好处是保留基座模型的先验知识、同时抑制过拟合。

    🧪 训练数据从哪来：合成的

    攻击者拿不到受害者的模型和系统，也就没法采集真实数据来训练。论文的解法是利用刚发现的周期性自己合成训练集（Algorithm 1）：

    • 从公开语料（UltraChat、NQ-Open、SIQA、SQuAD2、ChatGPT-Roles）取输入输出文本对，组成语料 C；
    • 对每个 token 的时间戳按高斯分布累积（ctime += N(1, σ²)），模拟 TPOT 的自然抖动，得到周期性时序；
    • 以概率 p 删除事件、以概率 p 在均匀分布的时间点插入随机 token，模拟漏检与多检；
    • 把数值的时序信号编码成文本提示，与文本一起组成 (提示, 标准答案) 训练对。例如时序 {1.3, 1.2} 与 token {Hello, World} 编码成 1 3:Hello<s>1 2:World<s>。

    论文在合成数据上把超参数扫了一遍：噪声概率 p 在 10%～40% 的宽范围内性能稳定，超过 50% 才开始下降；周期抖动 σ = 0.08 时最好（σ 太小等于强制严格周期，σ 大于 0.5 则周期性被削弱到模型学不到）；基座模型换成开源的 Llama-3.1-8B 或闭源的 GPT-4o-mini 性能差不多，说明这一层的效果主要来自任务本身，而不是某个特定模型。

    🔗 还原输入顺序：LLMB

    输出文本还原出来之后，还剩输入。输入 token 的集合 KP 已经拿到了，缺的是顺序。论文拿它类比 bag-of-words 模型：词袋丢掉了顺序但保留了语义结构，主题模型（如 LDA）就是这么用的。问题是顺序丢失会伤到句子本身，论文举的例子是 A chased B 与 B chased A——token 集合相同，语义相反。

    论文的落点是输入与输出在同一个上下文里相互关联：LLM 常常先把问题复述一遍再回答，所以输入文本对输出文本存在可学习的依赖。于是把任务写成另一个 seq2seq：

    实现方式是微调出 LLMB：把无序的 token 列表编码成 <s> 分隔的文本序列，把已经还原出来的输出文本插在最前面当上下文，让模型推断每个 token 的位置。

    训练数据同样靠合成：取语料里的输入 I，把它的 token 顺序随机打乱得到 KP’，再用一个通用 LLM 生成对应的输出 O’，于是 (KP’, O’, I) 就是一条监督样本。

    📊 评估：准确到什么程度

    实验环境是 Intel 13900K（5.8GHz，BIOS microcode 0x129）+ RTX 3060 12GiB + 32GiB 双通道 DDR4-3200，Ubuntu 22.04 / Linux 5.18.0-38、驱动 525.89.02、CUDA 12.0；微调放在一台 H800 云服务器上。受害模型是 5 个主流 LLM（Gemma2-9B、Llama-3.1-8B、Falcon3-10B、Mistral-7B、Phi-3.5-mini-3B），数据集是 5 个公开语料，合计 212,535 个 token，按 60/20/20 划分训练、验证、测试。

    指标分三个粒度：字符级的 Levenshtein 相似度（LS，等于 1 减编辑距离）、token 级的 ROUGE-1 / ROUGE-L、语义级的句向量余弦相似度 φ。为了确定 φ 到多少算泄漏，论文在 Prolific 上招募 100 名参与者，对 50 个样本做人工投票，得出 φ 与隐私暴露程度的线性关系（皮尔逊相关 0.771），取 φ > 0.77 作为攻击成功的判定阈值，ASR 就是超过该阈值的样本比例。

    🏁 主结果

    论文 Table 1 的汇总行（5 个模型 × 5 个数据集的平均）：

    方向 平均长度 R1 RL LS φ ASR
    输出还原 165 token 96.3% 96.3% 94.8% 98.7% 99.1%
    输入还原 24 token 89.9% 85.8% 82.7% 98.0% 99.9%

    对照摘要里的另一组口径：平均编辑距离在输出与输入上分别是 5.2% 与 17.3%。也就是说输出基本可逐字还原，输入能还原语义但字符级有出入。论文对输入侧的差距给了明确解释：输入还原是一个排列问题，搜索空间随输入长度按阶乘增长（约 O(NI!)）。

    这一点在数据里看得最清楚：

    数据集 平均输入 token 数 输入 LS 备注
    SQuAD2 180～209 32.2%～34.4% 长输入，字符级最差
    NQ-Open 12～13 79.8%～91.4% 短输入，还原很好
    UltraChat 19～21 84.3%～90.2% 同上

    但即使是最差的一格（Phi-3.5-mini on SQuAD2，R1 51.0%、LS 32.2%），余弦相似度仍有 92.1%，ASR 96.4%——语句的主题与语义没有被漏掉。

    论文还检查了 prefill 批大小的影响：batch size 从 32 涨到 256，各指标只在 4% 的范围内波动；batch 很小时精度略降，因为合成训练数据假设输入 token 是随机排列的，而小 batch 会让输入分批顺序执行、呈现出更强的顺序性，偏离了训练分布。

    🧹 消融：每个部件值多少

    配置 相对完整版的变化 说明
    去掉时序信号的预处理（一阶差分） LS −3.0%（输出）/ −1.0%（输入） 去噪前的归一化有贡献
    完全不喂时序信号 TD LS −12.7%（输出）/ −1.2%（输入） token 列表与时序必须融合
    去掉 LLMA，只用 KD 拼文本 LS −10.3% 模型去噪比规则去噪值钱
    LLMB 去掉还原出的输出上下文 LS −17.1% 上下文依赖是输入还原的主要依据
    去掉 LLMB，直接把 KP 当结果 LS −46.4% 没有排序模型基本等于没有输入还原

    还有一组更基础的对照：只用侧信道数据（Pure SCA）时，输入还原只到 R1 50.4%、LS 29.8%、φ 66.1%、ASR 29.3%；加上模型与输出上下文之后是 R1 82.8%、LS 76.2%、φ 96.9%、ASR 99.7%。纯侧信道拿到的是线索，文本还得靠语言模型补全——这也和本文的方法论一致。

    🧰 框架与硬件

    论文在 10 个主流本地推理框架上验证，CPU 路径全部成功，GPU 路径 9 个成功：

    维度 结果
    CPU 推理 10 / 10 成功（llama.cpp 的 φ 输出 99.5% / 输入 95.2%）
    GPU 推理 9 / 10 成功，唯一失败的是 HuggingFace Transformers
    失败原因 它把 embedding 查表放在 GPU 上做，CPU 缓存侧信道探不到
    硬件 14900K / 13900K / 12700KF 三台机器，输入还原的 φ 均不低于 96.5%，ASR 100%（该表两栏标号疑似互换，见后文口径一节）
    量化 F16 / Q8_0 / BF16 / F32 四种，φ 在 96.2%～99.3% 之间
    操作系统 Ubuntu 22.04、Windows 11、Debian 12（Docker 内）均可复现

    这组结果说明攻击不依赖某个特定框架的实现细节，真正的前提只有一条：embedding 在 CPU 上查表。

    💬 真实例子

    论文展示的还原样本里，有几个细节很能说明问题：

    • who played freddy krueger in the 2010 nightmare on elm street? 在论文的示例图里三项指标都是 100%。其中 freddy krueger 这类专有名词并没有出现在合成训练集里，模型是从侧信道给出的 token 线索里拼出来的；
    • How can I manage my weight and avoid gaining excess body fat? 被还原成 How can I manage my weight and avoid excess body fat?：少了一个 gaining，语义不变（φ 98%、R1 96%、LS 87%）；
    • what rank is an e5 in the air force? 被还原成另一种语序（φ 87%、R1 78%、LS 28%）：内容没丢，排列变了；
    • 失败的例子集中在语义相似度 64%～76% 的区间，典型表现是词序错乱、出现多余的 header、Zoeken 这类无关 token——正是噪声污染留下的痕迹。

    论文据此指出，这种能力足以窃取 PII（个人身份信息）：能还原专有名词、能容忍同义替换与语序变化，语义相似度高而字符相似度偏低，说明泄漏的是内容而不是形式。

    🛡️ 对策与局限

    🚧 论文建议的三种缓解

    措施 做法 代价
    禁用 zero-copy 加载 不让框架用 mmap 映射模型文件，切断共享内存这条路 llama.cpp 加载延迟性能下降 17%；同时跑两个以上实例时内存开销增加约 32%
    部署 RBAC 限制模型文件内存页的共享范围，只允许指定程序共享，可用 eBPF 内核钩子按会话认证 现有本地推理框架没有这项能力，需要改造
    硬件隔离缓存 用 Intel CAT（Cache Allocation Technology）切分 LLC，把 LLM 与其余进程隔开 只有服务器级 Xeon 提供，消费级平台拿不到；而本地 LLM 恰恰主要跑在消费级机器上

    三条路的共同问题是一样的：缓解手段要么伤性能，要么在目标平台上不存在。这也解释了论文为什么把它当作一个未被防御的现实威胁来报告，而不是一个已被修补的历史漏洞。

    🧱 论文承认的边界

    • 输入还原的字符级精度不高：受缓存攻击的时间分辨率与 prefill 并行执行限制，长输入的可读性有限；但在接近 6000 字符的长文本上，输入还原的语义 φ 平均仍有 94.8%、ASR 为 99.1%；
    • 换用其他 CPU 侧信道有额外门槛：Prime+Probe 一类冲突型攻击只有 set 级空间分辨率，而 embedding table 远大于缓存的路数，一个 set 会映射到多行，候选空间会膨胀；没有共享内存时，ASLR 与不连续的页帧分配还会打乱 set 与行的对应关系，需要额外的运行时画像；
    • GPU 侧 embedding 目前打不到：离散 GPU 的缓存与 CPU 不保持一致，需要 GPU 缓存攻击原语（例如 Invalidate+Compare），但那类原语同样有 set 冲突的问题。不过论文也留了一句：NVIDIA 驱动的显存页分配随机性较小、起始地址稳定，反而有利于学习地址映射。

    ✅ 总结

    本地 LLM 的输入输出文本，可以从 CPU 缓存的访问模式里读出来：embedding 查表暴露 token 的值，自回归解码的时序暴露 token 的顺序，剩下的事情交给两个微调过的语言模型去做——一个融合时序与 token 列表去噪还原输出，一个利用输入输出的上下文依赖给乱序的输入 token 排序。

    三个值得记住的要点：

    1. 泄漏点在访存模式上：embedding 是查表而不是乘法，查哪一行是可控的、可观察的；
    2. 性能优化顺带送出了攻击面：zero-copy 加载是 llama.cpp 这类框架的默认行为，也是攻击者拿到共享内存的捷径；
    3. 侧信道只是线索，语言模型负责补全：纯侧信道数据的输入还原 ASR 只有 29.3%，加上语言模型与输出上下文后到 99.7%——语义的补全能力本身就是攻击效力的一部分。

    如果把这篇和我们之前精读的 Hermes Attack 放在一起看，两条路线正好互补：Hermes 站在 CPU 与 GPU 之间的 PCIe 总线上抓明文流量，偷的是模型本身（结构、超参数、权重）；这篇站在 CPU 缓存上观察访存模式，偷的是使用模型过程中产生的内容（prompt 与回答）。共性是同一个结论——部署方式决定了数据流经哪些共享硬件，而那些共享硬件才是真正需要加密或隔离的地方。
