Rust OS 入门：从 main 到 _start

Posted on 2026-09-01 In 计算机基础 , Rust Views: Word count in article: 6.4k Reading time ≈ 12 mins.

师兄很早之前就推荐了这个项目学习，最近终于有时间来体验一下。看完第一节感觉还是对自己对计算机的了解很有帮助，于是整理这份笔记。

本文内容整理自 Philipp Oppermann 的《Writing an OS in Rust》系列教程（https://os.phil-opp.com/），配合个人学习笔记结构化为中文说明，示例与结论均可在该教程中溯源。

📚 基本概念速读

名称 定义 省流
std Rust 标准库，依赖操作系统提供文件、网络、线程、println! 等能力 站在 OS 肩膀上
core 不依赖操作系统的 Rust 基础库：基本类型、Option/Result、Iterator OS 里也能用的那一半
no_std 声明当前 crate 不自动链接 std 只用 core
panic_handler no_std 下必须自己提供的 panic 处理函数 崩溃了怎么办
crt0 C Runtime 0，负责程序启动环境初始化的启动代码，其中定义了入口符号 _start 启动的”保洁员”
_start 程序真正的入口符号，由链接器定位，定义在 crt0 启动代码中 一切从这开始
no_main 告诉 Rust 不要按普通程序的方式寻找 main() 入口我自己定
Target Triple 描述目标平台的”架构-厂商-OS-ABI”四元组 给谁编译

🧩 main() 不是程序真正的入口

这是理解 Rust OS 最重要的一步：main() 是应用程序逻辑的入口，而不是 CPU/OS 意义上的最底层入口。

普通程序的实际调用链是：



graph TD
    A["OS Loader / 内核"] -->|"跳转到 ELF 入口点"| B["crt0 中的 _start"]
    B -->|"初始化环境（栈 / argc / argv / TLS）"| C["Rust Runtime / libc"]
    C --> D["main()"]

也就是说：当 CPU 开始执行你的程序时，它进的不是 main()，而是链接器指定的入口符号 _start（该符号由 crt0 启动代码定义）。main() 只是这条链上”最后被调用”的那个普通函数。

🧩 std、core 与 no_std

Rust 标准库可以理解成两层：



graph TD
    S["std 标准库"] --> S1["操作系统相关：文件 / 网络 / 线程"]
    S --> S2["println! / Vec / String"]
    S --> C["core 核心库"]
    C --> C1["基本类型 / Option / Result / Iterator"]
    C --> C2["基本 trait / panic 基础机制"]

关键理解：core 不是直接和硬件交互的库，而是一个不依赖操作系统的 Rust 基础库。它可以运行在 Linux、Windows、裸机、嵌入式甚至 OS Kernel 中。std 则建立在 core 等基础设施之上，大量依赖操作系统提供的能力。

_start 的几个关键修饰符

修饰符 作用
#[unsafe(no_mangle)] 关闭 name mangling，保证最终符号名就是 _start
pub 符号对外可见，链接器/汇编器能找到它
extern "C" 使用 C ABI / calling convention
-> ! 永不返回：入口没有调用者，return 无处可去

关于 name mangling：Rust 默认会把函数名改写成带 crate 名和类型信息的符号，例如 fn start() 可能变成 _ZN3blog_os5start...，但链接器/bootloader 想找的是字面量 _start，所以必须 no_mangle。

🧩 crt0 与 _start 的区别

这是最容易混淆的一对概念：

  • _start：一个具体的入口函数/符号，定义在 crt0 启动代码中，“从哪里开始”。
  • crt0：一套负责程序启动的 C runtime 启动代码，“开始之后帮你做什么”。

关系：crt0 包含 _start——_start 不是 crt0 之外的下一层，而是 crt0 里定义的那个入口函数：

一句话记忆：_start = crt0 的入口点（从哪里开始），crt0 = 包含 _start 的一整套启动代码（开始之后帮你做什么）。

🧩 栈从哪里来？

栈并不是”单纯申请一块内存，然后保存一个地址”，要分情况：

  • OS 环境下：操作系统负责分配/映射虚拟内存、设置栈区域、设置 CPU 栈指针寄存器（x86-64 上是 RSP = 栈顶地址），之后 push / call / sub rsp, ... 都通过 RSP 操作栈。
  • Rust OS 中：bootloader/kernel 需要自己完成这部分初始化。

所以可以记成：

栈本质上是一块内存区域，而 CPU 通过栈指针寄存器（x86-64 的 RSP）知道当前栈在哪里。

_start 之所以写 loop {} 而不是 return，也是因为：程序入口没有调用者，栈上没有”返回地址”可供 return 使用。

🧩 链接器与链接错误

编译器与链接器的分工

编译器负责把源代码变成目标文件；链接器负责把这些目标文件和库组合成最终可执行文件。

为什么会出现链接器错误

因为你在 #![no_std] + #![no_main] 之后，仍然使用 x86_64-unknown-linux-gnu 这个 target。它意味着”我要生成一个 Linux 用户程序”，于是链接器默认认为需要 crt0、libc、Linux runtime；而你的程序没有 std、没有 libc、没有 main，于是报：

一种临时方案：手动传链接器参数

含义：cargo → rustc → linker → -nostartfiles，告诉链接器不要自动加入 C startup files：

各平台参数为什么不同

平台 可执行格式 默认入口 禁用 C startup
Linux ELF _start -nostartfiles
Windows PE mainCRTStartup /ENTRY:_start + /SUBSYSTEM:console
macOS Mach-O 自定义 -e __start（配合 -static、-nostartfiles）

因为它们的可执行文件格式、ABI、默认启动方式、链接器都不同。

为什么”不推荐”这个方法

-nostartfiles 只是告诉链接器”别给我 crt0”，但你仍然在 Linux 环境下运行。_start 里可能没有：

  • 初始化栈
  • 设置 TLS
  • 初始化运行时
  • 准备程序参数
  • 完成 libc 初始化

结果往往是：编译成功，运行崩溃。因为你在”假装自己是 Linux 程序”，却没有提供 Linux 程序应有的启动环境。

Host 与 Target

  • Host：运行编译器的机器，例如 Windows x86-64。
  • Target：你希望程序运行的机器，例如 x86_64-blog_os 裸机 kernel。

这种”在一种平台上编译出另一种平台程序”的做法叫交叉编译（cross compilation）。

🧩 两种启动链的最终对比



graph TD
    subgraph 普通Rust程序
        A1["硬件"] --> B1["操作系统"]
        B1 --> C1["ELF/PE loader"]
        C1 --> D1["crt0"]
        D1 --> E1["Rust runtime"]
        E1 --> F1["main()"]
    end
    subgraph RustOS
        A2["硬件"] --> B2["BIOS / UEFI"]
        B2 --> C2["Bootloader"]
        C2 --> D2["初始化 CPU / 栈"]
        D2 --> E2["_start()"]
        E2 --> F2["kernel_main()"]
        F2 --> G2["你的操作系统"]
    end

普通 Rust 程序要删掉的是 std、Rust runtime、crt0 这一整段”操作系统提供的环境”；Rust OS 里，这一段的职责由 bootloader + kernel 自己承担。

⚠️ 附：--target 与 --all-targets 不要混

Cargo 中：

  • --target：编译目标平台，例如 x86_64-unknown-linux-gnu。
  • --all-targets：Cargo package 中要构建哪些类型的目标（library、binary、test、bench、example）。

两者完全不是一个概念。

✅ 总结

no_std 是”不使用 Rust 标准库”；no_main 是”不让 Rust 按普通程序方式处理 main“；_start 是你自己定义的底层入口；crt0 是普通用户程序启动时帮你完成环境初始化的启动代码；而真正写 OS 时，我们连 crt0 都不要，而是让 bootloader + kernel 自己负责启动环境。
